# OpenSpec: Telegram Data Platform

## 2. `proposal.md`

### Change: telegram-data-platform

#### Цель

Реализовать data-платформу для сбора публикаций из 2 000 Telegram-каналов, обработки сообщений, извлечения ссылок, обогащения текста ML-моделями и предоставления аналитических витрин в Apache Superset.

#### Scope

В рамках проекта необходимо реализовать:

1. Сбор исторических и новых сообщений Telegram.
2. Сохранение исходных данных в Parquet.
3. Инкрементальный сбор с перекрытием диапазонов, дедупликацией и периодической сверкой истории.
4. Нормализацию данных в DuckDB.
5. Таблицы `messages`, `channels`, `message_links`, `message_meta`.
6. Обогащение сообщений тремя моделями Hugging Face.
7. Оркестрацию процессов через Apache Airflow.
8. Проверки качества данных через Great Expectations.
9. Аналитические витрины в DuckDB.
10. Подключение Apache Superset.
11. Мониторинг, логирование, алертинг и восстановление после сбоев.
12. Запуск компонентов через Docker Compose с постоянным хранением данных на host.

#### Не входит в первую версию

- Kafka и потоковая обработка.
- Kubernetes.
- Распределенное хранилище.
- Полноценный графовый движок.
- Собственное обучение ML-моделей.
- Анализ изображений, аудио и видео.
- Автоматическое скачивание и анализ содержимого внешних URL.
- Автоматическая классификация идеологии, пока не определены категории и методика проверки качества.

#### Критерии успеха

- Повторный запуск сбора не создает дубли сообщений.
- Ошибка одного канала не останавливает сбор остальных.
- После сбоя сбор возобновляется с сохраненного состояния.
- Все сообщения имеют устойчивый ключ.
- Результаты ML содержат версии моделей и оценки классов.
- Ошибочные записи обнаруживаются проверками качества.
- Витрины пересчитываются без повторного сбора Telegram.
- Superset использует подготовленные аналитические данные.
- Данные сохраняются после перезапуска контейнеров.
- Результаты и состояние pipeline можно проверить по журналу запусков.

## 3. `design.md`

### 3.1. Архитектура

Компоненты системы:

- Apache Airflow — оркестрация.
- Telegram collector — сбор сообщений через выбранный и проверенный механизм доступа к Telegram.
- Parquet — сырой слой Bronze.
- DuckDB — структурированные данные, результаты обогащения и аналитические витрины.
- Hugging Face Transformers + PyTorch — локальный inference.
- Great Expectations — Data Quality.
- Apache Superset — BI.
- PostgreSQL — метаданные Airflow и Superset.
- Docker Compose — запуск сервисов.

### 3.2. Слои данных

#### Bronze

Путь:

`/data/bronze/telegram_messages/`

Назначение: сохранение исходных результатов сбора.

Файлы должны включать идентификатор канала, исходные поля сообщения, время сбора, идентификатор запуска и версию схемы.

Организация файлов:

`channel_id=<id>/collection_date=YYYY-MM-DD/`

Требования:

- Не изменять уже опубликованные файлы Bronze.
- Записывать файлы атомарно.
- Сохранять информацию о происхождении данных.
- Повторный сбор может создавать повторные записи в Bronze.
- Дедупликация выполняется при загрузке в DuckDB.
- Повторная обработка Bronze не требует обращения к Telegram.

#### Silver

Реализуется как нормализованные таблицы DuckDB:

- `channels`
- `messages`
- `message_links`
- `message_meta`

Назначение: единая структурированная модель данных.

#### Gold

Реализуется как аналитические витрины DuckDB:

- `mart_channel_activity_daily`
- `mart_message_sentiment_daily`
- `mart_message_toxicity_daily`
- `mart_message_emotions_daily`
- `mart_channel_content_daily`
- `mart_domain_mentions_daily`
- `mart_channel_link_edges`
- `mart_pipeline_health_daily`

### 3.3. Правила инкрементального сбора

Для каждого канала хранить состояние:

- `channel_id`
- `last_successful_message_id`
- `last_successful_run_at`
- `last_seen_message_id`
- `last_reconciliation_at`
- `collection_status`
- `last_error`

Алгоритм:

1. Получить последнее сохраненное состояние канала.
2. Определить диапазон новых сообщений.
3. Начать сбор с перекрытием ранее обработанного диапазона.
4. Сохранять результаты в Bronze.
5. Проверять полноту записи.
6. Обновлять `messages` по ключу `(channel_id, message_id)`.
7. Обновлять метаданные канала.
8. Фиксировать состояние сбора только после успешной публикации данных.
9. При ошибке повторять попытку с ограниченным числом повторов и задержкой.
10. Периодически сверять недавнюю историю, а также запускать расширенную сверку по настраиваемому расписанию.

Размер перекрытия должен быть параметром конфигурации. Он не должен считаться гарантией обнаружения всех изменений.

Периодическая сверка должна позволять обнаруживать пропуски и изменения ранее опубликованных сообщений. Обнаружение удаленных сообщений реализуется только в пределах возможностей используемого источника.

### 3.4. Правила обработки сообщений

- Основной ключ: `message_key`.
- Формирование ключа: стабильное кодирование `source`, `channel_id`, `message_id`.
- Внутри DuckDB ключ сообщения уникален.
- `content_hash` используется для обнаружения одинакового содержимого, но не как первичный ключ.
- Повторная публикация одинакового текста в разных сообщениях не считается автоматическим дублем.
- Изменение текста сообщения обновляет текущую запись `messages`.
- Если необходима история изменений, она хранится отдельно в будущем расширении `message_revisions`.
- Обогащение должно пересчитываться при изменении исходного текста или версии модели.

### 3.5. Ограничения DuckDB

DuckDB используется как аналитическое хранилище для одного сервера.

Требования:

- Все процессы используют один согласованный путь к файлу базы.
- Одновременные операции записи из разных DAG-ов должны быть сериализованы.
- Тяжелый inference выполняется вне транзакций публикации данных.
- Временные результаты сначала записываются в staging-файлы.
- Публикация таблиц выполняется контролируемой задачей записи.
- При росте конкурентной нагрузки пересмотреть архитектуру хранения.

Файл базы:

`/data/warehouse/telegram.duckdb`

Резервное копирование должно выполняться согласованным способом, с проверкой восстановления. Нельзя копировать активно изменяемый файл базы как обычный произвольный файл и считать такую копию гарантированно корректной.

## 4. Спецификация `data-model/spec.md`

### Requirement: Channels

Система MUST хранить справочник Telegram-каналов.

Таблица `channels`:

| Поле | Тип DuckDB | Назначение |
|---|---|---|
| `channel_id` | VARCHAR | Первичный ключ источника |
| `username` | VARCHAR | Username канала, если доступен |
| `title` | VARCHAR | Название канала |
| `description` | VARCHAR | Описание |
| `channel_url` | VARCHAR | Ссылка на канал |
| `is_active` | BOOLEAN | Участвует ли канал в сборе |
| `first_seen_at` | TIMESTAMP | Первое обнаружение |
| `last_seen_at` | TIMESTAMP | Последнее обнаружение |
| `last_message_at` | TIMESTAMP | Время последней известной публикации |
| `created_at` | TIMESTAMP | Время создания записи |
| `updated_at` | TIMESTAMP | Последнее обновление |

Метаданные, недоступные из источника, должны иметь значение NULL, а не выдумываться.

### Requirement: Messages

Система MUST хранить по одной актуальной записи на уникальное сообщение.

Таблица `messages`:

| Поле | Тип DuckDB | Назначение |
|---|---|---|
| `message_key` | VARCHAR | Первичный ключ |
| `channel_id` | VARCHAR | Ссылка на `channels` |
| `message_id` | BIGINT | ID сообщения в канале |
| `message_date` | TIMESTAMP | Время публикации |
| `edited_at` | TIMESTAMP | Время редакции, если доступно |
| `text` | VARCHAR | Текст сообщения |
| `content_hash` | VARCHAR | Хеш нормализованного содержимого |
| `message_url` | VARCHAR | Ссылка на сообщение |
| `views_count` | BIGINT | Просмотры, если доступны |
| `forwards_count` | BIGINT | Пересылки, если доступны |
| `replies_count` | BIGINT | Ответы, если доступны |
| `has_media` | BOOLEAN | Наличие медиа |
| `media_type` | VARCHAR | Тип медиа, если известен |
| `is_deleted` | BOOLEAN | Подтвержденный статус удаления |
| `first_collected_at` | TIMESTAMP | Первое получение |
| `last_collected_at` | TIMESTAMP | Последнее получение |
| `updated_at` | TIMESTAMP | Последнее изменение записи |

Ограничения:

- `message_key` уникален и не равен NULL.
- `channel_id` и `message_id` обязательны.
- `message_date` обязателен для опубликованного сообщения, если источник предоставляет дату.
- Счетчики не должны быть отрицательными.
- Отсутствующие счетчики хранятся как NULL.
- Текст сообщения может быть пустым, например для публикаций с медиа.
- `content_hash` не используется для объединения разных сообщений.

### Requirement: Message links

Таблица `message_links`:

| Поле | Тип DuckDB | Назначение |
|---|---|---|
| `link_id` | VARCHAR | Устойчивый ID найденной ссылки |
| `message_key` | VARCHAR | Сообщение-источник |
| `raw_url` | VARCHAR | Исходный URL |
| `normalized_url` | VARCHAR | Нормализованный URL |
| `domain` | VARCHAR | Извлеченный hostname |
| `link_type` | VARCHAR | telegram, external, invite, unknown |
| `position_start` | INTEGER | Начальная позиция в исходном тексте |
| `position_end` | INTEGER | Конечная позиция |
| `extraction_version` | VARCHAR | Версия извлекателя |
| `extracted_at` | TIMESTAMP | Время извлечения |

Правила:

- Сохранять все вхождения ссылок, включая повторяющиеся.
- Позиции должны соответствовать одной документированной системе индексации, например Unicode code points в исходной строке.
- Сохранять исходный URL независимо от нормализации.
- Не удалять query-параметры без явного правила.
- Извлекать ссылки повторно при изменении текста или версии извлекателя.
- Ошибки разбора URL должны быть наблюдаемыми.
- Автоматическое обращение к внешним URL не входит в эту задачу.

### Requirement: Message metadata and enrichment

Таблица `message_meta` хранит результаты задач обогащения.

Одна запись представляет один результат одной версии задачи для одного сообщения.

| Поле | Тип DuckDB | Назначение |
|---|---|---|
| `enrichment_id` | VARCHAR | Первичный ключ результата |
| `message_key` | VARCHAR | Сообщение |
| `task_name` | VARCHAR | Например, toxicity, sentiment, emotion |
| `label` | VARCHAR | Основная метка, если применима |
| `scores_json` | JSON | Оценки всех классов |
| `confidence` | DOUBLE | Оценка выбранной метки, если применима |
| `model_name` | VARCHAR | Имя модели Hugging Face |
| `model_version` | VARCHAR | Зафиксированная ревизия модели |
| `inference_version` | VARCHAR | Версия реализации inference |
| `input_hash` | VARCHAR | Хеш входного текста |
| `processed_at` | TIMESTAMP | Время обработки |
| `status` | VARCHAR | success, failed, skipped |
| `error_message` | VARCHAR | Причина ошибки |
| `threshold_version` | VARCHAR | Версия правил интерпретации меток |

Ограничения:

- `message_key`, `task_name`, `model_version`, `inference_version`, `input_hash` обязательны для успешно обработанной записи.
- `scores_json` должен содержать оценки классов, полученные от модели.
- Все оценки должны быть конечными числами в диапазоне от 0 до 1.
- `confidence` может быть NULL, если у результата нет одной выбранной метки.
- Для ошибок сохраняется `status=failed` и краткая причина.
- Ошибка одной модели не должна блокировать результаты других моделей.
- Повторный inference не должен создавать дубли для одинаковой комбинации сообщения, задачи, модели, версии inference и входного хеша.
- При изменении текста или версии модели результат должен считаться устаревшим и пересчитываться.

### Семантика результатов моделей

**Toxicity**

Модель: `cointegrated/rubert-tiny-toxicity`.

Тип задачи: multilabel.

Классы: `non-toxic`, `insult`, `obscenity`, `threat`, `dangerous`.

Сохранять исходные оценки каждого класса. Не трактовать `non-toxic` как простое логическое отрицание всех остальных классов.

**Sentiment**

Модель: `cointegrated/rubert-tiny-sentiment-balanced`.

Классы: `negative`, `neutral`, `positive`.

Сохранять оценки всех классов. Реализовать отдельный адаптер модели, проверенный на тестовых примерах. Использовать sigmoid и выбор метки по правилам карточки модели, а не применять softmax по умолчанию.

**Emotion**

Модель: `cointegrated/rubert-tiny2-cedr-emotion-detection`.

Тип задачи: multilabel.

Классы: `no emotion`, `joy`, `sadness`, `surprise`, `fear`, `anger`.

Сохранять оценки всех классов. Пороговое решение по каждой эмоции должно быть настраиваемым и версионируемым. Не считать `no emotion` обычной эмоцией.

### Версионирование моделей

При развертывании необходимо:

1. Зафиксировать конкретный commit SHA каждой модели Hugging Face.
2. Сохранить модель и токенизатор в локальном кеше или каталоге моделей.
3. Зафиксировать версии Python, PyTorch и Transformers.
4. Запретить автоматическое обновление модели до последней ревизии при обычном запуске DAG.
5. Хранить конфигурацию модели отдельно от кода inference.
6. Добавить smoke tests на фиксированном наборе примеров.

## 5. Спецификация `telegram-ingestion/spec.md`

### Requirement: Initial backfill

Система MUST поддерживать первоначальный сбор доступной истории для 2 000 каналов.

- Список каналов хранится в конфигурации или в таблице реестра источников.
- Каналы обрабатываются независимыми задачами или группами.
- Параллельность регулируется конфигурацией Airflow.
- Ошибки отдельных каналов не прерывают весь backfill.
- Прогресс фиксируется отдельно для каждого канала.

### Requirement: Incremental collection

- Сбор запускается по расписанию.
- Для каждого канала используется собственное состояние.
- Диапазон сбора включает перекрытие ранее обработанных сообщений.
- Данные сохраняются в Bronze до обновления состояния сборщика.
- Повторный запуск безопасен.
- После частичного сбоя задача может повториться без потери ранее сохраненных данных.

### Requirement: Reconciliation

Периодическая сверка должна повторно проверять недавние диапазоны истории и выявлять пропуски.

Частота и размер диапазона задаются конфигурацией.

Расширенная сверка истории должна иметь отдельный режим запуска, чтобы не перегружать регулярный сбор.

### Requirement: Rate limits and retries

- Ограничивать параллельные запросы к источнику.
- Использовать backoff при временных ошибках.
- Не выполнять бесконечные повторы.
- Различать временные ошибки, отсутствие доступа и недоступность канала.
- Не обходить механизмы ограничения доступа.
- Сохранять диагностические сообщения без секретов.

## 6. Спецификация `orchestration/spec.md`

### DAG 1: `telegram_backfill`

Назначение: первичная загрузка истории.

Задачи:

1. `load_channel_registry`
2. `select_channels_for_backfill`
3. `collect_channel_history`
4. `write_bronze_partition`
5. `validate_bronze_output`
6. `update_collection_state`
7. `publish_run_metrics`

### DAG 2: `telegram_ingestion`

Назначение: регулярный сбор новых сообщений.

Задачи:

1. `load_active_channels`
2. `read_channel_cursors`
3. `collect_incremental_messages`
4. `write_bronze`
5. `validate_bronze`
6. `update_collection_state`
7. `emit_collection_metrics`

Параметры:

- `schedule`
- `overlap_size`
- `max_parallel_channels`
- `retry_count`
- `retry_delay`
- `request_timeout`
- `reconciliation_window`

Значения должны быть конфигурируемыми.

### DAG 3: `telegram_normalization`

Назначение: преобразование Bronze в структурированные таблицы.

Задачи:

1. `discover_unprocessed_partitions`
2. `read_bronze`
3. `normalize_channels`
4. `normalize_messages`
5. `deduplicate_messages`
6. `extract_message_links`
7. `validate_silver`
8. `publish_silver`
9. `record_processing_state`

Повторная обработка одной партиции должна быть безопасной.

### DAG 4: `telegram_enrichment`

Назначение: обогащение новых и изменившихся сообщений.

Задачи:

1. `select_messages_for_enrichment`
2. `load_local_models`
3. `run_toxicity_inference`
4. `run_sentiment_inference`
5. `run_emotion_inference`
6. `validate_inference_results`
7. `publish_message_meta`
8. `record_enrichment_metrics`

Модели должны обрабатываться независимо. Для каждого задания используются пакетная обработка и ограничение размера батча.

Пустые тексты обрабатываются по явному правилу, например `skipped` с соответствующей причиной, а не как обычные предсказания.

### DAG 5: `telegram_analytics_marts`

Назначение: обновление витрин.

Задачи:

1. `refresh_channel_activity_daily`
2. `refresh_sentiment_mart`
3. `refresh_toxicity_mart`
4. `refresh_emotion_mart`
5. `refresh_domain_mentions`
6. `refresh_channel_link_edges`
7. `refresh_pipeline_health`
8. `validate_gold`
9. `publish_marts`

### DAG 6: `telegram_reconciliation`

Назначение: сверка истории и восстановление пропусков.

Задачи:

1. `select_channels_for_reconciliation`
2. `collect_reconciliation_window`
3. `compare_collected_ids`
4. `write_missing_records`
5. `schedule_reprocessing`
6. `record_reconciliation_result`

### Общие правила Airflow

- Не передавать большие DataFrame через XCom.
- Через XCom передавать только небольшие параметры, идентификаторы запусков и ссылки на артефакты.
- Не запускать тяжелые ML-модели в Scheduler или Webserver.
- Использовать отдельные worker-процессы для inference.
- Настроить `execution_timeout`, `retries`, `retry_delay` и лимиты параллельности.
- Не допускать одновременной записи разных DAG-ов в одну таблицу DuckDB.
- Для записи использовать staging и контролируемую публикацию.
- Хранить идентификатор запуска в каждой операции записи.

## 7. Спецификация `data-quality/spec.md`

Great Expectations должен использоваться для проверки Bronze, Silver и Gold.

### Bronze checks

- Схема содержит обязательные поля.
- ID канала и сообщения не пусты.
- Даты имеют допустимый тип.
- Формат файлов читается.
- Число записей соответствует метрикам сбора.
- Файл не пуст, если сборщик сообщил о наличии сообщений.
- Нет необъяснимого резкого падения объема.
- Время сбора присутствует.
- Идентификатор запуска присутствует.

### Silver checks

Для `channels`:

- `channel_id` уникален и не NULL.
- `is_active` не NULL.
- URL, если задан, имеет допустимый формат.
- Метаданные не заменяются выдуманными значениями.

Для `messages`:

- `message_key` уникален и не NULL.
- `channel_id` не NULL.
- `message_id` не NULL.
- `message_date` корректен, когда доступен.
- Счетчики неотрицательны.
- Нет ссылок на несуществующие каналы.
- `content_hash` соответствует принятому алгоритму.
- Доля пустых текстов отслеживается отдельно, а не считается безусловной ошибкой.

Для `message_links`:

- `link_id` уникален и не NULL.
- `message_key` ссылается на существующее сообщение.
- `position_start` неотрицателен.
- `position_end` больше `position_start`.
- `raw_url` не пуст для извлеченной ссылки.
- `link_type` принадлежит допустимому набору.
- Доля ошибок извлечения отслеживается.

Для `message_meta`:

- `enrichment_id` уникален.
- `message_key` существует.
- `task_name` принадлежит разрешенному набору.
- `status` принадлежит разрешенному набору.
- `scores_json` валиден для успешных предсказаний.
- Все оценки конечны и находятся в диапазоне [0, 1].
- `model_version` и `inference_version` заполнены для успешных результатов.
- Не возникает дублей по логическому ключу результата.

### Gold checks

- Витрины имеют ожидаемую схему.
- Гранулярность каждой витрины соблюдается.
- Даты принадлежат допустимому диапазону.
- Суммы счетчиков неотрицательны.
- Обновление витрин завершается в ожидаемое время.
- Нет неожиданных провалов количества строк.
- Доли классов моделей находятся в контролируемых диапазонах.
- Источники и периоды в витринах соответствуют Silver.

### Типы результатов проверок

- `PASS` — проверка пройдена.
- `WARN` — отклонение допустимо, но требует внимания.
- `FAIL` — критическое нарушение.

Критические проверки должны блокировать публикацию соответствующей витрины. Некритические отклонения должны записываться и отправляться в мониторинг.

### Реестр проверок

Результаты Great Expectations должны быть доступны в виде истории запусков с:

- названием набора проверок;
- именем таблицы или слоя;
- временем запуска;
- результатом;
- количеством проверенных записей;
- количеством неуспешных записей;
- идентификатором Airflow run;
- кратким описанием ошибки.

Great Expectations отвечает за качество данных; Airflow отвечает за исполнение проверок и реакцию на их результат.

## 9. Superset

Superset должен подключаться к DuckDB через проверенный SQLAlchemy-совместимый способ подключения.

Требования:

- Использовать витрины Gold для основных дашбордов.
- Не выполнять тяжелые преобразования сырых сообщений в интерактивных запросах.
- Настроить доступ к аналитическим данным отдельно от инфраструктурных метаданных.
- Не открывать доступ к таблицам состояния сбора обычным аналитическим пользователям.
- Настроить резервное копирование метаданных Superset.

### Минимальные дашборды

1. **Channel Activity** — активность каналов, динамика публикаций, свежесть данных.
2. **Sentiment** — распределение тональности по каналам и периодам.
3. **Toxicity** — динамика оценок токсичности и категорий.
4. **Emotions** — распределение эмоций по каналам и времени.
5. **External Domains** — часто упоминаемые домены и динамика ссылок.
6. **Pipeline Health** — успешность DAG-ов, ошибки, задержки и результаты проверок.

## 11. Общие требования к реализации coding agent

1. До написания кода прочитать все спецификации.
2. Не реализовывать все компоненты одним большим скриптом.
3. Использовать отдельные модули для ingestion, normalization, enrichment, quality и marts.
4. Не зашивать конфигурацию каналов, расписания и пороги моделей в код.
5. Не хранить секреты в репозитории.
6. Для каждого преобразования добавить тесты.
7. Для каждого DAG описать входные данные, выходные данные и правила повторного запуска.
8. Для каждого изменения схемы предусмотреть совместимость или миграцию.
9. Не добавлять новые инфраструктурные компоненты без обоснованной необходимости.
10. Не считать задачу завершенной без тестов, проверок качества и документации.
11. Сначала реализовать небольшой вертикальный срез на нескольких каналах, затем масштабировать до 2 000.
12. Не использовать фиктивные результаты сбора или ML в production-пайплайне.

## 12. Definition of Done

Проект считается готовым к первому production-запуску, когда:

- Все шесть DAG-ов реализованы и протестированы.
- Первоначальная загрузка и инкрементальный сбор работают.
- Данные проходят Bronze → Silver → Gold.
- Все четыре основные таблицы соответствуют схемам.
- Все три модели выполняются локально и сохраняют версии результатов.
- Great Expectations проверяет каждый слой.
- Витрины строятся повторяемо.
- Superset отображает реальные данные из витрин.
- Критические сбои обнаруживаются алертами.
- Перезапуск задач не приводит к потере данных или неконтролируемому дублированию.
- Резервная копия успешно восстановлена в тестовом сценарии.
- Реализация документирована и запускается по инструкции из чистого окружения.
